Ticket 06 · vertical slice

The public page

done

Any one pet’s page can be switched on at its own URL and handed to a kennel, a sitter or a family member. It is off by default, it shows nothing about the handler, and switching it off kills the link at once.

Blocked by

04  An entry exists: the universal log form and the feed

What to build

Before the switch is thrown the handler is shown exactly what the page will and will not reveal, so they are not guessing what they are publishing. Copying the link is one action. Switching it off stops the link working immediately, and switching it back on returns the same URL — a link already given to someone keeps working, because the slug was claimed at insert.

A visitor holding the link needs no account. They see the pet’s photo, name, species, breed, colour and age, and every entry as a date and a title with the next due date where there is one. They do not see the handler’s name, email or contact details; they do not see notes or clinic names; and the date of birth is coarsened to a month and year, so the page carries no more identifying detail than it needs. A due date prints in neutral grey with no stamp — publishing an accusation about the handler is not what the page is for. The page is unsigned: it reads “Shared by the pet’s owner”, with no handler name at all.

That is a fact about the database rather than a promise the frontend makes. The request runs as anon, reading both public views in one transaction — they are the only route in, so a bug in backend code still cannot return a note or a vet name. A slug that does not exist, is not public, or belongs to an archived pet all return the same 404: a visitor cannot distinguish “never existed” from “switched off”.

The page is a document, not an app screen: no navigation, no avatar, no sign-in prompt beyond the footer mark. It shares the app’s type and colour and none of its furniture. There is no per-entry visibility switch — the page shows all entries or none.

Endpoints in this slice

GET/public/pets/{slug}
PATCH/pets/{id}

Acceptance criteria

  • Every pet’s public page is off by default; creating a pet publishes nothing
  • Switching one pet’s page on does not affect any other pet
  • The About tab states what the page will and will not reveal before the switch is thrown
  • The public link is shown only when the page is on, and can be copied in one action
  • Switching the page off makes the link 404 immediately
  • Toggling public off and on returns the identical slug
  • The public request reads both views in one transaction as anon
  • The public payload contains no note, no vet, no id and no exact date of birth
  • The date of birth appears only as a month and year, with the age derived
  • A slug that is private, archived or absent returns the same 404, with nothing to tell the three cases apart
  • A visitor with no account and no cookie can read the page
  • A due date on the public page renders in neutral grey with no overdue stamp
  • The page renders no navigation, no avatar and no sign-in prompt
  • The public page has a desktop and a mobile layout

Done means

Every criterion above passes at the two seams the PRD fixed: the HTTP API against a real Postgres with RLS, the views and the constraints all live, and the rendered screen with HTTP stubbed at the network boundary. No test mocks the database, no test mocks a hook, and no test asserts on component internals — a test that breaks when nothing observable changed is a bug in the test. The desktop and mobile layouts are built together in this slice, not as a pass at the end: the slice is not done until both exist.
