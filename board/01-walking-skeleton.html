Ticket 01 · vertical slice

Walking skeleton: a signed-in shell over live RLS

ready-for-agent

A person can create an account, sign in, and land on a page that greets them by name — with the session in an httpOnly cookie and every query already running under Postgres row-level security.

Blocked by

Nothing — can start immediately

What to build

This slice proves the security model before any product feature depends on it. A visitor submits a name, email and password; the backend calls Supabase Auth server-side, receives the tokens, and writes them into an httpOnly; Secure; SameSite=Lax cookie. The browser never sees a token and no Supabase client ships to it. On the next load the app asks the backend who it is and renders the handler’s name in the shell.

The load-bearing piece is the per-request database dependency: every authenticated request opens a transaction, assumes the authenticated role and sets the caller’s verified JWT claims, so auth.uid() resolves and all four RLS policies fire in Postgres exactly as they would have for a browser talking to PostgREST. Nothing hand-rolls an ownership check, and a forgotten filter in backend code returns nothing rather than another handler’s pets.

Both test harnesses land here too, because every later slice leans on them: the API tests drive the FastAPI test client against a throwaway Postgres with all three migrations applied, with nothing stubbed — RLS live, views live, constraints live; the screen tests render routes with HTTP mocked at the network boundary.

async with pool.acquire() as conn:
    async with conn.transaction():
        await conn.execute("set local role authenticated")
        await conn.execute(
            "select set_config('request.jwt.claims', $1, true)", claims_json
        )
        yield conn   # auth.uid() now resolves; RLS applies to every query

From the PRD prototype — the whole mechanism, recorded so it is not re-derived later. The public-page path in ticket 06 uses the same shape with set local role anon.

Deviation from the PRD build order. The PRD puts the signup and sign-in screens in slice 02. They exist here as bare, unstyled forms — just enough to exercise the cookie and make this slice demoable in a browser. Ticket 02 replaces them with the drawn screens.

Acceptance criteria

  • A new account can be created; the on_auth_user_created trigger creates the handler row, so there is never a session without a profile
  • Signing in sets an httpOnly, Secure, SameSite=Lax cookie; no token is readable from JavaScript in the page
  • GET /me returns the signed-in handler’s name, and 401s with no cookie
  • The backend refreshes an expired access token silently and re-issues the cookie; the frontend holds no token parsing, no expiry timer and no refresh logic
  • Two seeded handlers, one dataset: handler B’s queries return none of handler A’s rows — enforced by RLS, not by a WHERE clause in application code
  • A deliberately omitted ownership filter in backend code returns nothing rather than another handler’s data
  • The backend never connects as service_role for application data
  • No Supabase client, key or domain reaches the browser
  • API tests run against a real Postgres with all three migrations applied — no mocked database
  • Screen tests render a route with HTTP stubbed at the network boundary — no mocked hooks, no assertions on component internals
  • The signed-in shell renders the handler’s name in both the desktop and the mobile layout

Done means

Every criterion above passes at the two seams the PRD fixed: the HTTP API against a real Postgres with RLS, the views and the constraints all live, and the rendered screen with HTTP stubbed at the network boundary. No test mocks the database, no test mocks a hook, and no test asserts on component internals — a test that breaks when nothing observable changed is a bug in the test. The desktop and mobile layouts are built together in this slice, not as a pass at the end: the slice is not done until both exist.
