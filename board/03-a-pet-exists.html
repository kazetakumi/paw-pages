Ticket 03 · vertical slice

A pet exists: add, list, About tab

ready-for-agent

A handler adds a pet with just a name and a species, sees it on the home screen, and can open its About tab to correct anything they guessed.

Blocked by

01  Walking skeleton: a signed-in shell over live RLS

What to build

Species is free text, so a rabbit, a bird or a tortoise is as welcome as a dog. Breed, sex, colour and date of birth are all optional and can be filled in later — a handler should be able to start logging before they have gathered every detail. A rescue with a guessed birthday is neither a blank field nor a lie: the date can be marked approximate, and the flag stays visible next to the age. Age is derived at read time and never stored, so it can never go stale and nobody is ever asked to correct it.

Every pet claims a slug at insert whether or not its public page is ever switched on, so toggling the page off and on later returns the same URL. The name is slugified and four random characters appended; a unique violation regenerates the suffix and retries, bounded at five attempts. The database enforces shape and uniqueness; the backend owns generation. This retry loop is the one thing in v1 that earns a unit test, because provoking a collision through the API is awkward and the loop is easy to get subtly wrong.

The home screen starts here as pet cards — one account covers the whole household, however many pets that is. A pet with no photo shows a clean initial-letter avatar, so the record is usable before anyone gets round to a picture. The About tab holds identity, and later the public switch and archiving, kept off the feed so the settings do not clutter the record.

Endpoints in this slice

GET/pets
POST/pets
GET/pets/{id}
PATCH/pets/{id}

Acceptance criteria

  • A pet can be created with a name and a species alone
  • Species accepts any free text within its length cap — nothing branches on it
  • Breed, sex, colour, date of birth and the approximate flag can each be set at creation or added later
  • Marking a date of birth approximate with no date is rejected, matching the database constraint
  • Age is derived from the date of birth on read and shown beside it with the approximate flag visible
  • Every pet gets a slug at insert, valid against the database’s shape check, whether or not it is public
  • Two pets with the same name resolve their slug collision without error
  • Slug generation’s retry loop is unit-tested against a forced collision
  • The home screen lists the handler’s active pets as cards, desktop and mobile
  • A pet with no photo renders an initial-letter avatar
  • The About tab shows the pet’s identity fields, and every one of them can be edited afterwards
  • A second handler cannot read, update or delete any of the first handler’s pets
  • Field-level 422s surface next to the right field rather than as a raw constraint violation

Done means

Every criterion above passes at the two seams the PRD fixed: the HTTP API against a real Postgres with RLS, the views and the constraints all live, and the rendered screen with HTTP stubbed at the network boundary. No test mocks the database, no test mocks a hook, and no test asserts on component internals — a test that breaks when nothing observable changed is a bug in the test. The desktop and mobile layouts are built together in this slice, not as a pass at the end: the slice is not done until both exist.
