Ticket 09 · vertical slice

Account: details, export, deletion

ready-for-agent

A handler can change what the app calls them, take everything they have entered away as one file, and leave — shown exactly what will be erased first.

Blocked by

07  Pet photos

What to build

The account screen holds the display name, the email address and the password, so losing access to an old inbox does not lock a handler out and a password can be rotated if they think it is compromised. It shows when they joined and how many pets and entries the account holds, so they have a sense of what is in it.

Three personal fields are optional and stay unset unless filled in: a date of birth, from which age is derived so nobody is asked to keep an age up to date, and a gender and a nationality, both free text. None of them drives anything in the app. They are collected because they were asked for, and they are named explicitly on the delete screen for exactly that reason.

The export is one archive, built on request and streamed: a JSON file of the handler, their pets and every entry, plus every photo. There is no job queue in v1 and at this scale there does not need to be. A handler’s pets’ history is theirs regardless of what happens to this app.

Deletion removes the photos first, then the auth user — which cascades handlers to pets to entries. Order matters: once the rows are gone, nothing knows which files to remove. Deleting the auth user is the only thing the service-role key is ever used for; anything else it touches is a bug.

Endpoints in this slice

PATCH/me
PATCH/me/email
PATCH/me/password
GET/me/export
DELETE/me

Acceptance criteria

  • The display name, email address and password can each be changed
  • The screen shows the join date and the pet and entry counts
  • Date of birth, gender and nationality are optional and unset by default; age is derived from the date of birth and never stored
  • The export contains every pet, every entry and every photo, in one streamed archive
  • The delete screen names exactly what will be erased, including the three optional personal fields
  • Deleting an account removes the stored photos first, then the auth user
  • After deletion the handler, pet and entry rows are gone and no storage object is left behind
  • The service-role key is used only for deleting the auth user, never to read or write application data
  • Every account endpoint returns 401 with no cookie
  • The account screen has a desktop and a mobile layout

Done means

Every criterion above passes at the two seams the PRD fixed: the HTTP API against a real Postgres with RLS, the views and the constraints all live, and the rendered screen with HTTP stubbed at the network boundary. No test mocks the database, no test mocks a hook, and no test asserts on component internals — a test that breaks when nothing observable changed is a bug in the test. The desktop and mobile layouts are built together in this slice, not as a pass at the end: the slice is not done until both exist.
