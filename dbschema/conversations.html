pawpages_conversations

One row per chat thread. Holds the whole exchange as a raw transcript, plus enough summary — a title, which pets came up — to list it in a sidebar without reading the transcript at all.

Rows live  0 — not migrated RLS  planned Primary key  id New for  v2

Columns

ColumnTypeNotes
iduuiddefault gen_random_uuid()
handler_iduuid required → pawpages_handlers.id, on delete cascade.
titletext Optional. Null until the handler renames it or the app derives one from the first turn.
pet_idsuuid[] Optional. Which pets came up in this conversation. No foreign key — see below.
transcripttext required default ''. Newline-delimited JSON — one line per turn, appended as the conversation goes.
created_at / updated_attimestamptz default now(). updated_at is bumped every time a turn is appended, which is what lets the sidebar sort by recency without a separate last_message_at.
Why transcript is text, not jsonb jsonb has to hold one valid JSON value. True JSONL — an independent JSON object per line, appended without touching the ones before it — only works as text. The tradeoff: appending a turn is still a full UPDATE on the row (Postgres has no in-place text append), so write cost grows with conversation length. Fine for a personal journal's chat lengths; would need revisiting if conversations get long-running.
Why pet_ids is an array, not a join table Chosen for simplicity over enforcement. It means no foreign key, no on delete cascade — if a pet is deleted, nothing automatically removes its id from every conversation's array. That cleanup, if it matters, is the app's job (a trigger could do it, but none exists yet).
Why title and transcript aren't split into two tables A large text value gets TOASTed — stored out of line — automatically past roughly 2 KB, so listing id, title, pet_ids for a sidebar never reads the transcript bytes even sharing one table. Renaming a title doesn't rewrite the transcript either: an UPDATE only touches the columns that changed, and an untouched TOASTed value keeps its existing pointer. Splitting would only pay off if the two needed different RLS or different retention, and neither does yet.

Why the on-delete behaviour isn't the same for all three An unclaimed upload is disposable — cascading it away with its conversation is correct. A pet or an entry is never disposable just because the chat that created it got deleted, so those two use set null: the provenance link is dropped, the record stays.
