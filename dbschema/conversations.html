pawpages_conversations

One row per chat thread: a title, which pets came up, and when it was last active. The turns themselves live in pawpages_messages, one row each.

transcripttext Unused since 0010. Was newline-delimited JSON, one line per turn. Left in place only because rule 9 forbids dropping a column on the live project; nothing reads or writes it.
created_at / updated_attimestamptz default now(). updated_at is bumped by the app every time a turn is saved, which is what lets the sidebar sort by recency without a separate last_message_at.
Why the turns moved out to their own table 0008 kept the whole exchange here as one JSONL text column. Three things made that the wrong shape once chat had tools. Appending a turn rewrote the whole value, since Postgres has no in-place text append, so every save got slower as the chat grew. The sidebar's fallback title had to read every conversation's full transcript to find its first user line. And there was no natural place for tool calls and their results. One row per turn in pawpages_messages fixes all three.
Why updated_at is bumped by the app, not the trigger alone The touch_updated_at trigger only fires when this row is updated. Saving a turn is now an insert into pawpages_messages, so save_turn also runs update … set updated_at = now() on the conversation.
Why pet_ids is an array, not a join table Chosen for simplicity over enforcement. It means no foreign key, no on delete cascade — if a pet is deleted, nothing automatically removes its id from every conversation's array. That cleanup, if it matters, is the app's job (a trigger could do it, but none exists yet).

Why the on-delete behaviour isn't the same for all three An unclaimed upload is disposable — cascading it away with its conversation is correct. A pet or an entry is never disposable just because the chat that created it got deleted, so those two use set null: the provenance link is dropped, the record stays.
