pawpages_uploads

One row per photo a handler sends in — from the chat composer's attach button, or straight from a pet's edit screen. Tracks it from the moment it lands in storage until (if ever) it becomes a pet's or an entry's photo.

Rows live  0 — not migrated RLS  planned Primary key  id Bucket  pet-photos (existing)

Why this exists

A photo attached in chat can't always be filed straight to {pet_id}/{filename} — the same convention pets and entries already use — because the assistant may not yet know which pet the message is about when the upload happens. This table is the staging area: the object lands under {handler_id}/uploads/{filename} immediately, and stays there. Nothing moves the file once it's claimed — a pet's or an entry's photo_path just points straight at wherever it already is.

Why no updated_at The only thing that ever changes on this row is the claim, and claimed_at already records when. A second timestamp tracking "last touched" would say nothing claimed_at doesn't.

Constraints worth knowing

NameRule
pawpages_claimed_by_one_target claimed_by_entry_id is null or claimed_by_pet_id is null — never claimed by both at once.
pawpages_claim_is_complete claimed_at is set exactly when at least one claim column is set. Mirrors pawpages_archive_is_complete on pets: the pair travels together or neither is there.

No reverse FK from entries or pets

This table points at what claimed it, not the other way around — pets and entries don't gain a column pointing back at pawpages_uploads. They already carry the storage path directly in photo_path, which is the only thing serving a photo needs. If you ever need to ask "was this pet's photo one that came through chat," the answer is pawpages_uploads.storage_path = pawpages_pets.photo_path — a lookup by value, same as it's always been.

What isn't handled here

An upload that's never claimed is an orphaned object with no cleanup job — the same gap that already exists for a deleted pet's or entry's photo. on delete cascade on claimed_by_entry_id / claimed_by_pet_id removes this tracking row when the thing that claimed it is deleted, on the assumption the app deletes the underlying storage object at the same time, as it already does for entry photos (see entries). Storage has no foreign keys of its own, so that promise is only as good as the app code that keeps it.

Storage policy — not yet written

The four handler policies from 0004 key off (storage.foldername(name))[1] matching a pet id the handler owns, so they don't cover {handler_id}/uploads/… — segment one there is a handler id, not a pet id. This needs one new, additive storage policy granting a handler read/write/delete on objects under their own {handler_id}/uploads/ prefix, in the same spirit as 0007's policy for published entry photos. Nothing on 0003/ 0004 gets touched.

Row level security — planned

PolicyRule
pawpages_handler_owns_uploads all where handler_id = (select auth.uid()), same on using and with check — the same shape as pawpages_handler_owns_pets.
