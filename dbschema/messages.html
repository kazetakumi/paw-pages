pawpages_messages

One row per item in a conversation — every user message, assistant message, tool call and tool output, in order. Replaces the JSONL transcript column that pawpages_conversations carried in 0008.

RLS  on Primary key  id New for  v2

Columns

ColumnTypeNotes
idbigint generated always as identity. Also the turn order — see below.
conversation_iduuid required → pawpages_conversations.id, on delete cascade.
handler_iduuid required → pawpages_handlers.id, on delete cascade. Copied from the conversation.
typetext required One of user_message, assistant_message, function_call, function_call_output. Replaced role in 0011.
contentjsonb required The whole item exactly as it's replayed to the model: a {role, content} message, a function_call (call_id, name, arguments), or a function_call_output (call_id, output).
created_attimestamptzdefault now()
Why order by id, not created_at A user turn and its reply are saved in the same transaction, and now() is the transaction's start time, so both rows get the same created_at. An identity column always increases, so it gives a reliable order.
Why handler_id is here when the conversation already has it So the RLS policy can be a plain column check, the same shape as every other table's, instead of a join to the conversation on every read.
Why tool calls are stored, not just the text Without them the model's next turn sees "user asked, I said done" but not which tool it called, with what arguments, or what came back — exactly what a follow-up like "change that entry's date" needs. Storing every item means loading history is just every row's content in id order, replayed as is.
Why one type column, not role plus type 0010 had role, which only fits messages. A single type covers all four kinds with one check constraint and no "role only when it's a message" rule. The values are the Responses API's own item names (messages named by role), so the column and the jsonb use the same words. The chat UI reads only user_message and assistant_message; the model gets everything.

Indexes

IndexFor
pawpages_messages_conversation_idx (conversation_id, id) — loading one conversation's turns in order, and the sidebar's first-user-turn lookup.

Row level security

PolicyRule
pawpages_handler_owns_messages all. using: handler_id = (select auth.uid()). with check: the same, plus the conversation must be one the handler can see.
Why with check also looks at the conversation Without it, a handler could write a turn into someone else's conversation by using their own handler_id with that conversation's id. The exists subquery runs under pawpages_conversations' own RLS, so it only finds the handler's own threads.
