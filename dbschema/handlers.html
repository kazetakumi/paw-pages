pawpages_handlers

One row per signed-up person. A profile, not an account — email and password stay in auth.users and are never duplicated here.

Why the three optional fields exist Nothing in the app branches on gender or nationality — they were requested, so they are stored, optional, and unset by default. They are pure liability: collected, held, and deletable on request, which is why the account-deletion screen names them explicitly.

How the row appears

There is no insert path from the app. A trigger on auth.users creates the row the instant Supabase Auth creates the person, so a signed-in user without a profile is not a state that exists:

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function handle_new_user();

handle_new_user() is security definer — it runs before any session exists, so it needs the owner's rights to bypass RLS. It seeds name from raw_user_meta_data->>'name', falling back to the literal 'Handler' when signup didn't collect one. Its execute grant is revoked from anon and authenticated, so it cannot be called as a REST endpoint.

Row level security

PolicyRule
pawpages_handler_reads_self select where id = (select auth.uid())
pawpages_handler_updates_self update, the same condition on both using and with check
Two deliberate absences No insert policy — the row is created by the security-definer trigger, and nothing else should ever create one. No delete policy either — account deletion happens in auth.users and cascades down.
