Three tables, three views, row level security throughout, and one private storage bucket. Everything a handler can see is decided by Postgres, not by the frontend remembering to filter.

Everything lives in the public schema except the storage policies, which attach to storage.objects. There is no application server: the browser talks to PostgREST directly, which is precisely why the access rules have to live in the database.

Authentication

Supabase Auth owns credentials. This schema never sees a password.

Sign-up, sign-in, password hashing, sessions, refresh tokens, reset emails and email confirmation are handled by Supabase Auth in the auth schema. auth.users.id is the anchor every other table hangs from, and auth.uid() — which reads the caller's signed JWT — is what every policy compares against.

A trigger keeps the two halves in step, so there is never a signed-in user without a profile row:

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function handle_new_user();

handle_new_user() is security definer — it has to insert into handlers before any session exists, so it runs with the owner's rights and bypasses RLS. Its execute permission is revoked from anon and authenticated so it cannot be called as a REST endpoint.

Why due_closed_at exists

Entry titles are free text, so the database cannot tell that "Rabies booster" and "rabies" are the same series. Nothing can close a due date automatically — somebody has to say so. That is what this column records, and it is the entire reason the pet page has a Mark done button.

Overdue is therefore always: due_on < current_date and due_closed_at is null.

Constraints worth knowing

NameRule
due_after_it_happened A next-due date cannot precede the date the thing happened.
cannot_close_a_due_date_that_does_not_exist due_closed_at requires a due_on.

Indexes

Four, each written for a query a screen actually makes. Three are partial — they index only the rows that get read.

IndexServes
pets_handler_active_idx The pet list. where archived_at is null, so archived pets are not in the index at all.
pets_public_slug_idx Public page lookup by URL, limited to pets that are actually public and active.
entries_pet_feed_idx A pet's feed, newest first — (pet_id, happened_on desc, id desc). The id breaks ties so pagination is stable.
entries_open_due_idx The dashboard ledger. Only entries that still owe something: due_on is not null and due_closed_at is null.

Views

A view stores no data — it is a saved SELECT that re-runs on every read. These three exist for two different reasons.

due_items — one definition of "overdue"

The rule is needed on the dashboard and on every pet page. Written twice it drifts; someone adds the archived check in one place and a dead pet turns up in red. Written once, the screens cannot disagree.

select e.id as entry_id, p.id as pet_id, p.handler_id, p.name as pet_name,
       e.title, e.due_on,
       e.due_on - current_date as days_until,
       e.due_on < current_date as is_overdue
from entries e join pets p on p.id = e.pet_id
where e.due_on is not null
  and e.due_closed_at is null
  and p.archived_at is null;

It is security_invoker = true, so the caller's own RLS applies — a handler reading it sees only their pets, automatically.

public_pets & public_entries — the gate

RLS decides which rows someone can read. It cannot hide columns. The public page problem is entirely about columns: a visitor may see an entry's date and title, and must never see the note or the vet.

create view public_entries as
select p.slug, e.title, e.happened_on, e.due_on
from entries e join pets p on p.id = e.pet_id
where p.is_public and p.archived_at is null;

note, vet, due_closed_at and every row id are not filtered out — they are absent from the query. An anonymous visitor has no policy on entries at all, so there is no request they can craft that returns a note, even if the frontend has a bug.

public_pets does the same for the pet, and coarsens the birthday: it exposes Mon YYYY plus a precomputed age_years / age_months. The exact date never leaves the table.

Row level security

Enabled on all three tables. Four policies, all keyed to auth.uid().

PolicyTableRule
handler_reads_selfhandlers select where id = auth.uid()
handler_updates_selfhandlers update, same condition on both using and with check
handler_owns_petspets all where handler_id = auth.uid()
handler_owns_entriesentries all where the parent pet belongs to auth.uid()

Every policy wraps the call as (select auth.uid()). That lets Postgres evaluate it once per query rather than once per row, which matters as the entries table grows.

Two deliberate absences There is no insert policy on handlers — the row is created by the security-definer trigger, and nothing else should ever create one. There is no delete policy either: account deletion happens in auth.users and cascades down through handlers → pets → entries.

Storage

One private bucket. Photo visibility follows the pet, enforced by the same mechanism as everything else.

Bucketpet-photos
Publicfalse
Max file size5 MB
Allowed typesimage/jpeg, image/png, image/webp, image/heic
Path convention{pet_id}/{filename}

The path convention is load-bearing: the first folder is the pet's id, and every policy joins it back to pets using (storage.foldername(name))[1]. The comparison is done as text rather than casting to uuid, so a malformed path fails the policy quietly instead of raising an error at the user.

PolicyWhoRule
reads own pet photosauthenticatedThe pet's handler_id must equal auth.uid()

replaces own pet photosauthenticated
deletes own pet photosauthenticated
anyone reads photos of public petsanon + authenticated The pet must have is_public and archived_at is null
Why not a public bucket A public bucket gives every file a permanent world-readable URL — including photos of pets whose page is switched off, which quietly undoes the toggle. With these policies, turning a page off or archiving a pet stops the image resolving at the same instant the page goes dark. The cost is that files serve through the Storage API rather than straight off the CDN.

Migrations

Plain SQL in supabase/migrations/, committed to git. Run in order on an empty database, they produce exactly what is live.

FileWhat it did
0001_init.sql The three tables, four indexes, three views, RLS and its four policies, and the two triggers.
0002_harden_functions.sql Pinned search_path on touch_updated_at; revoked execute on both trigger functions from anon and authenticated; documented the two deliberate view exceptions.
0003_pet_photos_bucket.sql The bucket and its five storage policies.

The rule

Once a migration has been applied anywhere real, it is frozen — you write the next one. 0002 exists because the linter found problems in 0001 after it had already run. Editing 0001 would have left a file that no longer describes the database that exists.

Linter exceptions

Supabase's security linter reports two errors. Both are the design.

public_pets and public_entries are flagged as SECURITY DEFINER views, meaning they run with the owner's privileges and bypass RLS on the underlying tables. That is exactly what they are for — anonymous visitors have no policy on pets or entries, so these views are their only route in, and each exposes a fixed column list.

The lint-clean alternative would be granting anon a select policy on the tables with column-level grants. It is worse: it exposes handler_id and the exact date of birth, and makes the coarsened age impossible to compute. The reasoning is written into both views' comments so nobody "fixes" it later.

Left to the app

Things the database deliberately does not do.

ThingWhy not in the database
Slug generation The app slugifies the name and appends four random characters, retrying on the unique violation. The database only enforces shape and uniqueness.
Age display Derived from date_of_birth at read time. Never stored, so it cannot go stale.
Photo cleanup Deleting a pet cascades its rows, but the file in the bucket is not removed by that cascade. The app must delete the object, or a cleanup job must.
Anything scheduled There are no jobs, no cron, no sending. Due dates are read when someone opens the app, and that is the whole system.
